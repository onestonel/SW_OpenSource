# OCR 개선 보고서

영수증 사진 자동 인식(V2)을 고쳐 가며 **발견한 문제 → 원인 → 해결 방안 → 결과**를 회차마다 쌓는 문서입니다.
V2 제출 때 함께 냅니다. 코드 설명은 [server/app/ocr/README.md](../server/app/ocr/README.md)에 있습니다.

## 목표와 평가 방법

- **목표**: 사진에서 '영수증 만들기' 초안(가게 이름 · 합계 · 품목)을 만들어 **사람이 고칠 칸을 줄이는 것**.
  영수증은 '확인 중' 상태로 만들어지므로, 틀린 곳을 정확히 알려 주는 것(경고)도 목표에 포함합니다.
- **평가**: `python -m app.ocr.bench`로 정답 JSON과 비교합니다.
  - 가게 이름: 이름 유사도 0.8 이상이면 맞음 · 합계: 정확히 같아야 맞음
  - 품목: 금액 · 종류가 같고 이름 유사도 0.7 이상이면 맞음 → 정밀도 · 재현율로 **F1**
  - 완벽: 가게 · 합계 · 품목이 모두 맞은 장 비율
- **평가 데이터** (`server/app/ocr/samples/`)
  - `dev_`: 규칙을 고칠 때 보는 것 / `test_`: 고칠 때 보지 않는 것(점수만 잼)
  - 가짜 영수증 12장(`synth.py`로 그림, dev 6 · test 6) + 진짜 영수증 사진 26장(dev 15 · test 11)
  - 진짜 사진 26장은 가게 21곳입니다. 3회차까지의 21장은 test를 dev와 다른 가게로 골랐습니다(같은 가게인 에이스돈 2장은 둘 다 dev).
    4회차에 더한 마트형 5장(dev 1 · test 4) 중 test 2장(금촌농협 · 코스트코)은 dev에 있는 가게입니다(4회차 test 절).
    18장은 팀원이 이번 달에 폰으로 찍은 사진이고, 8장은 예전 영수증 사진(대부분 인터넷에 공개된 사진)입니다.
    식당 · 카페가 13장, 마트 · 매장 · 주유소가 13장입니다.
  - 진짜 사진은 대표자 이름 · 전화 · 카드번호 · 회원번호 등을 가리고, 위치 정보(EXIF)를 지운 뒤 넣습니다.
  - 1회차까지는 진짜 사진이 3~4장뿐이었습니다. 2 · 3회차 실험은 사진을 21장으로 늘린 뒤 다시 했고, 적은 사진으로 했던 결과는 폐기했습니다.

## 점수 변화

**0 · 1회차 (옛 데이터, Tesseract)**: 진짜 사진이 2 ~ 3장뿐이던 때라 가짜와 진짜를 합친 점수입니다(dev 8장 = 가짜 6 + 진짜 2, test 7장 = 가짜 6 + 진짜 1).

| 회차 | 내용 | dev 합계 | dev F1 | test 합계 | test F1 |
| --- | --- | --- | --- | --- | --- |
| 0 | 규칙 파서만 (출발점) | 75% | 0.78 | 86% | 0.80 |
| 1 | 좌표 기반 표 읽기 + 산수 검산 | 88% | 0.78 | 86% | **0.90** |

**2 ~ 4회차 (진짜 21장 기준)**: 진짜 사진을 21장(dev 14 · test 7)으로 늘린 뒤 다시 잰 값이라 위 표와 바로 비교할 수 없습니다. 가짜가 훨씬 쉬워서 진짜와 나눠 봅니다.
2회차 행은 3회차의 '기본'(Tesseract fast + 기본 전처리)과 같고, 3 · 4회차 행은 PaddleOCR(`unwarp=true` + 최소 전처리) 점수입니다.

| 회차 | 내용 | 진짜 dev 합계 | 진짜 dev F1 | 진짜 test 합계 | 진짜 test F1 | 가짜 F1 (dev · test) |
| --- | --- | --- | --- | --- | --- | --- |
| 2 | 전처리 단계 + Ablation → 기본 전처리 유지 · 열 읽기 버그 수정 | 4/14 | 0.44 | 2/7 | 0.42 | 0.96 · 0.94 |
| 3 | 엔진 비교 → **PaddleOCR + 최소 전처리로 교체 확정** · 숫자 열의 `O`→`0` 수정 | 9/14 | 0.72 | 3/7 | 0.68 | 0.96 · 1.00 |
| 4 | 파서 개선: 숫자 줄 품목 읽기(4-1) + 세금 줄 산수로 합계 찾기(4-2) → **확정** | **13/14** | **0.87** | **4/7** | **0.71** | 0.96 · 1.00 |

3회차의 교체는 규칙상 확정된 결정이고, 서버 기본값에는 아직 적용하지 않았습니다(3회차 8절).
4회차에 마트형 사진 5장(dev 1 · test 4)을 더한 데이터(진짜 dev 15 · test 11)로 3회차 파서와 4회차 파서를 비교하면
dev는 합계 10/15 → 14/15 · F1 0.73 → 0.88, test는 합계 3/11 → 5/11 · F1 0.70 → 0.72입니다(4회차 test 절).

## 1회차 — 좌표 기반 표 읽기 + 산수 검산 (2026-11-24)

### 1. 발견한 문제

진짜 영수증 사진을 처음 넣어 보니, 가짜 영수증(거의 만점)과 달리 크게 틀렸습니다.

| 샘플 | 가게 | 합계 | 품목 |
| --- | --- | --- | --- |
| dev_real_01 (마트, 15품목) | O | X | 11/15 (+5 엉뚱한 품목) |
| dev_real_02 (식당, 8품목) | X | X | 0/8 |
| test_real_01 (식당, 7품목) | X | X | 0/7 |

※ 사진 이름은 1회차 당시 기준입니다. 이때의 test_real_01(에이스돈 2번째 영수증)은 dev 가게와 같아서 지금은 dev_real_09로 옮겼고, 지금의 test_real_01은 다른 사진입니다.

dev 사진 2장의 줄별 판단 로그(`--show-errors`)를 보고 실패를 네 갈래로 나눴습니다. test 사진은 보지 않았습니다.

| # | 실패 모양 (실제 예) | 깨진 단계 |
| --- | --- | --- |
| ① | 숫자가 띄어 읽힘: `69, 000` · `2 .590` · `14, 720` → 69와 0으로 쪼개짐 | 파서가 글자 위치를 버리고 텍스트만 봄 |
| ② | 합계 줄을 못 찾음: `합 계`를 `가수 0, 계`로 읽음, `결제대상금액` 낱말 없음 | OCR 인식 품질 / 규칙 |
| ③ | 휜 사진에서 두 줄이 한 줄로 합쳐짐, 가게 이름 줄과 주소 줄이 합쳐짐 | 전처리 · 줄 묶기 |
| ④ | 숫자 오인식: `1,580` → `1,560`, `5,000` → `6,000` | OCR 인식 품질 |

### 2. 원인 분석과 방향 선택

파이프라인은 `사진 → 전처리 → OCR 엔진 → 줄 묶기 → 파서`입니다. 위 실패 중 **파서의 "규칙(낱말)이 모자라서" 틀린 것은 거의 없었습니다.**
가장 쉬운 대응은 실패할 때마다 규칙을 덧대는 것이지만, 이는 앞 단계의 실수를 사례마다 땜질하는 것이라 새 영수증에 일반화되지 않습니다.

검토한 방안 (일반화 효과 · 비용 기준):

| 방안 | 일반화 | 비용 | 판단 |
| --- | --- | --- | --- |
| 실패마다 규칙 추가 (①② 땜질) | 낮음 | 낮음 | 근본 해결이 아님 |
| **좌표 기반 표 읽기** | 높음 (표 구조는 가게와 무관) | 낮음 (엔진이 이미 좌표를 줌) | **1회차** |
| **산수 검산** | 높음 (계산 관계는 가게와 무관) | 낮음 | **1회차** |
| 전처리 강화 (영역 자르기 · 원근 보정) | 높음 | 중간 | 후보 (③) |
| 엔진 비교 · 교체 (EasyOCR, PaddleOCR, 유료 API) | 높음 | 중간 | 후보 (②④) |
| LLM 파서 (조장님 #35의 llama.cpp 구조 재사용) | 높음 | 중간~높음, 숫자를 지어낼 위험 | 후보, 산수 검산과 함께 |
| 학습 모델 (LayoutLM, Donut) | 가장 높음 | 라벨 수백 장 + 학습 | 이번 학기 범위 밖 |

어느 가게 영수증이든 통하는 두 가지 구조를 먼저 쓰기로 했습니다.
- **표 구조**: 금액은 '금액' 열에 세로로 줄 맞춰 찍힌다. 머리줄(`단가 수량 금액`)의 x 위치가 곧 열의 위치다.
- **계산 관계**: `단가 × 수량 = 금액`, `품목 합 = 합계`.

### 3. 구현

**① 좌표 기반 표 읽기** (`parser._read_columns`)

```
입력: 한 줄의 낱말 상자들  [양념갈비 x=40] [ㆍ x=240] [69, x=280] [000 x=315] [1 x=415] [69, x=510] [000 x=545]
머리줄에서 열 위치:          단가 x≈310       수량 x≈420       금액 x≈545  (이보다 왼쪽은 이름 칸)
처리: 낱말마다 가장 가까운 열에 넣고, 같은 열 조각은 잇고, 숫자 아닌 잡글은 버림
출력: (이름 '양념갈비', 단가 69000, 수량 1, 금액 69000)
```

- 엔진: Tesseract가 줄 상자 안에 **낱말 위치(`words`)**를 함께 넘기도록 바꿨습니다.
  처음에는 낱말 단위로만 넘기고 줄을 직접 묶었는데, 기울어진 사진에서 금액이 아래 줄로 밀려 가짜 샘플 점수가 떨어졌습니다(dev_06 3/4 → 0/4).
  그래서 줄 묶기는 Tesseract에 맡기고 낱말 위치만 추가로 쓰는 방식으로 바꿨습니다.
- 머리줄의 `금액`이 `금 액`처럼 쪼개져도 글자 단위로 찾습니다. `금액`을 아예 못 읽으면(`글이`) 줄마다 맨 오른쪽 숫자의 위치로 금액 열을 정합니다.
- 앞자리를 놓쳐 `000`만 읽힌 칸은 빈칸으로 보고, 빈 단가 · 수량은 금액에서 거꾸로 계산합니다.
- 이름 앞의 순번(`01*`, `08*.`, `12__`)과 잡글(`ㆍ`, `、`)을 뗍니다.
- 낱말 위치가 없는 입력(글자만 넣은 테스트, stub 엔진의 줄)은 이전과 똑같이 동작합니다.

**② 산수 검산** (`parser._reconcile`)

```
입력: 김밥  단가 1,580 × 1 ≠ 금액 1,560   →  후보 {1,560, 1,580}
      라면  단가 4,000 × 1 = 금액 4,000
      합계 5,580
처리: 품목 합이 합계와 정확히 맞는 조합 중 고친 칸이 가장 적은 것을 고름 (1,560 → 1,580이면 5,580으로 맞음)
출력: 김밥 금액 1,580 + 경고 "단가×수량으로 금액을 고쳐 합계와 맞췄습니다: '김밥' 1,560원 → 1,580원. 맞는지 확인해 주세요."
```

- 금액끼리 이미 합계와 맞으면 단가나 수량을 잘못 읽은 것이므로 초안은 그대로 둡니다.
- 맞는 조합이 없으면 고치지 않고 **어긋난 품목 이름을 경고**로 알려 사람이 그 줄만 보면 되게 합니다.
- 고친 칸은 반드시 경고로 남깁니다. 합계까지 잘못 읽으면 틀린 값에 맞춰 고칠 수 있기 때문입니다.
  (실제로 dev_real_01은 `3,850 → 3,890`, `73,550 → 73,590`처럼 단가와 합계에서 같은 5→9 오인식이 나왔습니다.)

테스트 6개를 추가했습니다(`server/tests/test_ocr.py`): 띄어 읽힌 숫자 · 잡글 · 순번 · 쪼개진 머리줄, 금액 열 추정, 금액 고치기, 고치지 않아야 할 때, 고친 칸이 가장 적은 조합 고르기, 맞는 조합이 없을 때 경고.

### 4. 결과

| 샘플 | 0회차 | 1회차 |
| --- | --- | --- |
| dev_real_01 | 합계 X · 11/15 (+5) | 합계 X · **13/15** (+4) |
| dev_real_02 | 합계 X · 0/8 | 합계 **O** · 1/8 (+5) |
| test_real_01 | 합계 X · 0/7 (+1) | 합계 X · **5/7** (+1) |
| 가짜 영수증 12장 | 거의 만점 | 그대로 (떨어지지 않음) |

- ① 띄어 읽힌 숫자는 해결됐습니다. 처음 보는 test 사진에서 품목이 0/7 → 5/7로 오른 것이 일반화된 근거입니다.
  다만 진짜 사진이 3장뿐이라 점수 변동이 크므로, 사진을 늘려 다시 재야 합니다.
- dev_real_02는 금액만 보면 8개 중 4개(69,000 · 6,000 · 3,000 · 12,000)를 맞게 읽었습니다.
  하지만 이름을 `도 ㅅ ^`, `공`, `칼 ㄴ`처럼 읽어서 채점에서는 틀림 + 엉뚱한 품목으로 셉니다. 이것은 **OCR 엔진의 한글 인식 문제**입니다.
- 경고가 실제로 틀린 줄을 가리키게 됐습니다. 예: dev_real_02의 `단가×수량과 금액이 다른 품목이 있습니다: '소주'` — 소주는 실제로 5,000원인데 6,000원으로 읽은 줄입니다.
- 산수로 금액을 고친 경우는 dev 사진에서 아직 나오지 않았습니다. dev_real_01은 합계 줄 자체를 못 찾았기 때문입니다(②).

### 5. 남은 문제와 다음 회차 후보

| 남은 문제 | 예 | 다음 방안 |
| --- | --- | --- |
| 합계 줄을 못 찾음 (②) | `가수 0, 계 73,590` | **세금 줄 검산**: dev_real_01에서 면세 27,960 + 과세 41,445 + 부가세 4,145 = 73,550 = 정답 합계. 합계 줄과 독립된 두 번째 합계 후보가 됨 |

## 2회차 — 영수증 전처리 + Ablation Study (2026-11-24)

### 1. 목표

1회차의 남은 문제 중 ③(휜 사진 · 배경 · 그림자)은 사진 단계의 문제입니다. 문서 스캐너식 전처리를 단계별로 넣고,
**각 단계가 실제로 점수를 올리는지** 켜고 끄며 재 봤습니다(Ablation Study).

### 2. 구현한 단계

모든 단계는 `PreprocessOptions`의 값 하나로 켜고 끕니다(`server/app/ocr/preprocess.py`). 단계 ②④⑤⑥은 OpenCV를 씁니다(`requirements-ocr.txt`에 추가).

```
사진 → ① EXIF 회전 · 흑백 → ② 영수증 영역 자르기 + 원근 보정 → ③ 크기 맞추기 → ④ 조명 평탄화
     → ⑤ 기울기 보정 → 명암 늘리기 → ⑥ 적응형 이진화 → OCR 엔진
```

| 단계 | 옵션 | 하는 일 |
| --- | --- | --- |
| ② 영역 자르기 | `crop=True` | 가장 큰 밝은 영역(종이)의 네 꼭짓점을 찾아 직사각형으로 편다. 못 찾으면 사진 전체를 읽고 경고를 남긴다 |
| ③ 크기 | `target_width=1400` | 잘라낸 영수증 폭을 고정한다 (영수증은 폭 · 한 줄 글자 수가 거의 정해져 있어 글자 크기가 비슷해짐) |
| ④ 조명 평탄화 | `flatten=True` | 글자를 지운 배경 밝기로 나눠 그림자를 없앤다 |
| ⑤ 기울기 보정 | `deskew=True` | ±8도 안에서 글자 줄이 가장 선명하게 수평이 되는 각도로 돌린다 |
| ⑥ 적응형 이진화 | `adaptive_threshold=True` | 주변 밝기 기준으로 흑백 두 색으로 바꾼다 |
| T: Sauvola | `TesseractEngine(thresholding=2)` | 전처리 대신 Tesseract 안의 흑백 나누기 방식을 바꾼다 |

함께 만든 도구:
- `python -m app.ocr 사진.jpg --prep crop flatten --save-steps 폴더` — 단계별 중간 사진 저장
- `python -m app.ocr.ablation` (하나씩 더하기 · 빼기), `--grid` (②④⑤⑥ 16가지 조합)

### 3. 실험 방법과 채택 규칙 (결과를 보기 전에 정함)

- dev 20장(가짜 6 · 진짜 14)으로만 비교하고, 가짜와 진짜를 따로 요약합니다. 진짜 dev 품목은 88개(할인 6줄 포함)라 품목 하나가 F1 약 0.01입니다.
- 비교 대상(기준)은 지금 기본 전처리(흑백 · 폭 1400~2000 · 명암 늘리기, ②~⑥은 모두 끔)와 Tesseract fast입니다.
- 후보는 `ablation`(하나씩 더하기 · 모두 · 모두에서 하나씩 빼기)과 `ablation --grid`(②④⑤⑥ 16가지 조합)에서 잰 모든 설정입니다.
- 아래를 **모두** 만족하는 설정만 기본값으로 켭니다. 3회차 엔진 비교와 같은 기준입니다.
  1. 진짜 dev 품목 F1 ≥ 기준 + 0.05
  2. 진짜 dev 엔진 점수(금액 인식률과 이름 인식률의 평균, 3회차 4절) ≥ 기준
  3. 진짜 dev 합계를 맞힌 장수 ≥ 기준
  4. 가짜 dev 품목 F1 ≥ 0.90이고 오류가 없음 (3회차 B 탈락 조건)
  5. 진짜 dev 14장 중 기준보다 사진별 품목 F1이 나빠진 장수 ≤ 나아진 장수 (평균이 사진 한두 장 덕분에 오른 경우를 거름)
- 여러 설정이 통과하면 진짜 dev F1이 가장 높은 것을 고르고, 0.02 이내로 비기면 켜는 단계가 적은 것을 고릅니다.
- 채택한 설정이 있으면 3회차 test에서 기준과 함께 한 번만 재고 3회차의 D 규칙으로 확정합니다. 없으면 기본값을 그대로 둡니다.

### 6. 결론

1. **기본값은 모두 끈 채로 둡니다.** 기준을 뺀 24가지 설정(두 표에 겹치는 ② · ④ · ⑤ · ⑥ 단독은 한 번만 셈) 중 채택 조건을 모두 만족한 것이 없습니다.
   조건 1(진짜 F1 ≥ 0.49)부터 아무도 넘지 못했고, 가장 높은 설정도 0.45(②⑥ · 모두 − ⑥)로 기준 0.44와 품목 하나 차이입니다.
   채택한 설정이 없으므로 test에는 기본 설정만 들어갑니다(3회차 6절에서 '기본'으로 잼).
2. **전처리는 숫자를 더 잘 읽게 하지만 초안 점수로 이어지지 않았습니다.** ② 자르기가 들어간 설정은 금액 인식률이 0.77 → 0.83 ~ 0.91로 올랐지만 진짜 F1은 0.33 ~ 0.45에 머뭅니다.
   사진마다 효과가 엇갈리기 때문입니다. 예를 들어 ②는 dev_real_10을 0/4 → 3/4로 올렸지만 dev_real_09는 5/7 → 0/7로 떨어뜨렸고, dev_real_11의 엉뚱한 품목을 +2 → +9로 늘렸습니다.
3. **②나 ⑥이 들어간 설정은 모두 깨끗한 가짜 영수증을 망칩니다**(가짜 F1 0.56 ~ 0.87, 기준 0.96). 이것만으로 조건 4에 걸립니다.
   ②와 ⑥이 없는 ③ · ④ · ⑤ · ④⑤는 가짜 점수는 지키지만 진짜 F1이 내려갑니다(0.35 ~ 0.40).
4. **단계끼리 서로 영향을 줍니다.** ④와 ⑥은 따로 켜면 진짜 F1이 0.39 · 0.41인데, 자르지 않고 함께 켜면 0.32(④⑥) · 0.28(④⑤⑥)로 가장 나쁩니다(가짜 F1도 0.56 · 0.63).
   하나씩 켜고 끄는 실험만으로는 이것을 놓칩니다.
5. **사진이 적을 때 본 약한 신호는 재현되지 않았습니다.** 진짜 사진 3장일 때 ②⑥이 합계를 모두 맞혀 후보로 남겼는데(3회차 후보에 넣은 이유),
   14장에서는 합계 5/14(기준 4/14) · F1 0.45(기준 0.44)였습니다.
6. Tesseract 안의 Sauvola 이진화는 혼자 쓰면 해롭고(진짜 F1 0.35 · 엔진 점수 0.58), ⑥과 함께 쓰면 이미 흑백이라 효과가 없습니다('모두'와 '모두 − T'가 같음). 후보에서 뺍니다.
7. **병목은 전처리 뒤에 있습니다.** 기준에서도 정답 금액의 77%가 엔진 원문에 있는데 품목은 88개 중 32개만 맞혔고, 엉뚱한 품목이 27개 붙었습니다.
   이름 인식률(0.62)과 엉뚱한 품목이 점수를 더 크게 좌우합니다. 3회차에서 같은 사진을 PaddleOCR로 읽으면 진짜 F1이 0.72까지 오른 것도 이를 뒷받침합니다.

### 7. 개선 방안 (다음 회차 후보, 우선순위 순)

| 순서 | 방안 | 근거 | 비용 |
| --- | --- | --- | --- |
| 1 | **엔진 비교** (Tesseract best · EasyOCR · PaddleOCR) | 전처리로는 진짜 F1이 오르지 않고, 이름 인식률이 0.62에 머묾 (결론 2 · 7) | bench 실행 (→ 3회차) |
| 2 | **합계 아래 줄 막기 + 세금 줄 검산**: 합계 줄 아래는 품목으로 보지 않고, '면세 + 과세 + 부가세 = 합계'를 두 번째 합계 후보로 씀 | dev_real_01(27,960 + 41,445 + 4,145 = 73,550) · dev_real_12(56,890 + 180,863 + 18,087 = 255,840) 모두 정답 합계와 정확히 일치. 엉뚱한 품목이 줄어야 산수 검산이 작동함 (결론 7) | 파서 수정 |
| 3 | **산수로 전처리 고르기**: 기준으로 읽어 품목 합 ≠ 합계면 다른 설정으로 다시 읽고 맞는 쪽을 채택 | 설정마다 맞히는 사진이 다름 (결론 2). 정답 없이 고를 수 있는 신호는 산수뿐. 2번이 먼저 돼야 효과가 있음 | 실패한 사진만 시간 2배 |
| 4 | **가짜 데이터 보강**: `synth.py`에 원근 · 말림 · 낮은 해상도 · 접힌 자국 | 가짜 dev_06이 ②의 실제 문제(그림자 + 자르기)를 찾아냄. 싸게 실험 수를 늘릴 수 있음 | synth 수정 |

말린 종이 펴기(dewarping)는 여전히 비용이 커서 보류하고, 화면에서 "영수증을 평평하게, 화면에 꽉 차게" 찍도록 안내하는 것을 프론트에 제안합니다.

### 2. 고르는 규칙 (실험 결과를 보기 전에 정함)

**규칙을 바꾼 점과 그 시점** (먼저 밝혀 둡니다)

처음에는 진짜 사진 4장(dev 3 · test 1)으로 이 비교를 한 번 했고, 사진을 21장으로 늘린 뒤 그 결과를 폐기하고 다시 했습니다.
아래 규칙은 처음 비교와 같고, 다시 하기 전(새 결과를 보기 전)에 다음만 바꿨습니다.
- C5 추가, D를 ①②③으로 바꿈(①의 여유 −0.02 → −0.05, 진짜 사진만), 2회차 전처리 채택에도 같은 규칙을 씀.
- D②(합계)는 처음 비교에서 PaddleOCR이 test 진짜 사진의 합계를 맞히고도 품목 수 조건에 걸린 것을 보고 넣었습니다. 즉 그 결과를 알고 정한 조건입니다.
- 정답 확인과 개인정보 가리기 확인을 위해 test 사진을 눈으로 봤습니다. test 사진의 OCR 결과는 보지 않았고, 그것으로 파서 규칙을 고치지 않았습니다.

**A. 엔진마다 대표 설정 하나 고르기 (dev 20장만 사용)**

후보 설정은 아래 목록으로 고정하고, 결과를 본 뒤 늘리지 않습니다. 2회차에서 채택한 전처리가 있으면 Tesseract fast · best에 그 설정을 더합니다.

| 엔진 | 후보 설정 |
| --- | --- |
| Tesseract fast · best | 전처리 {기준, ②⑥} |
| EasyOCR | `width_ths` {0.5(기본), 0.1} × 전처리 {기준, 최소, ②⑥} = 6개 |
| PaddleOCR | 문서 펴기(unwarping) {끔, 켬} × 낱말 상자 {끔, 켬} × 전처리 {기준, 최소, ②⑥} = 12개 |

- 전처리 '기준' = 지금 기본(흑백 · 폭 1400~2000 · 명암 늘리기), '②⑥' = 영역 자르기 + 적응형 이진화(2회차의 약한 후보),
  '최소' = EXIF 회전만(색 유지 · 크기 그대로 · 명암 그대로). 딥러닝 엔진은 원본에 가까운 사진이 나을 수 있어서 넣었습니다.
- PaddleOCR의 설정이 모두 속도 조건(B-1)에서 탈락하면, 가벼운 검출 모델(mobile)로 같은 설정을 한 번 더 잽니다. 이 예외도 미리 정해 둔 것입니다.
- **추가 (PaddleOCR 점수를 보기 전)**: 처음 목록은 6개였습니다. PaddleOCR 설치 후 API를 확인하다가 낱말 위치도 줄 수 있다는 것(`return_word_box`)을 알게 되어,
  EasyOCR의 `width_ths`와 같은 궁합 옵션으로 '낱말 상자'를 후보에 더했습니다. 이 시점까지 확인한 것은 사진 한 장의 속도와 상자 모양뿐입니다.
- 대표 설정 = 진짜 dev 품목 F1이 가장 높은 설정. 0.02 이내로 비기면 가짜 dev 품목 F1이 높은 쪽, 그래도 비기면 빠른 쪽.
- B의 탈락 조건은 **설정마다 먼저** 적용하고, 대표 설정은 탈락하지 않은 설정 중에서 고릅니다. 남는 설정이 없으면 그 엔진이 탈락합니다.
  (실험을 돌리는 중, 결과를 보기 전에 규칙 문장이 두 가지로 읽힐 수 있음을 발견해 명시했습니다. 위 PaddleOCR 예외 문구와 같은 뜻입니다.)

**B. 탈락 조건 (하나라도 걸리면 탈락)**

1. **속도**: dev 평균 처리 시간이 20초/장을 넘거나, 가장 느린 장이 40초를 넘음 (이 PC의 CPU 기준).
   지금은 API 요청 안에서 OCR을 기다리고(프록시 시간 제한이 보통 30~60초), V2 Worker로 옮겨도 사용자는 초안을 기다리기 때문입니다.
2. **깨끗한 영수증 실력**: 가짜 dev 품목 F1이 0.90 미만 (지금 기본은 0.96. 깨끗하게 인쇄된 영수증에서 품목 2~3개 넘게 더 틀리면 탈락).
   이 기준을 정할 때 2회차의 ②⑥ 점수(가짜 F1 0.86)를 이미 알고 있었다는 점을 밝혀 둡니다.
3. **안정성**: dev 사진 중 하나라도 오류로 결과를 내지 못함.

**C. 기본 엔진을 바꾸는 조건**

비교 대상(기본)은 Tesseract fast + 2회차에서 정한 기본 전처리입니다. 궁합 수정(3절)을 반영한 코드로 잰 점수를 씁니다.
도전자(대표 설정)가 아래를 **모두** 만족해야 바꿉니다.

1. 진짜 dev 품목 F1 ≥ 기본 + 0.05 (품목 약 5개)
2. 진짜 dev 엔진 점수(금액 인식률과 이름 인식률의 평균) ≥ 기본. 나아진 이유가 파서와의 우연한 궁합이 아니라 엔진의 인식 실력이어야 합니다.
3. 진짜 dev 합계를 맞힌 장수 ≥ 기본
4. B의 탈락 조건을 모두 통과
5. 진짜 dev 14장 중 기본보다 사진별 품목 F1이 나빠진 장수 ≤ 나아진 장수

여러 도전자가 통과하면 진짜 dev F1이 가장 높은 것을 고르고, 0.02 이내로 비기면 더 빠른 것을 고릅니다. 아무도 통과하지 못하면 기본을 유지합니다.

**D. test는 한 번만**

- 엔진마다 대표 설정 하나씩(2회차에서 채택한 전처리가 있으면 그것도)을 test 13장(가짜 6 · 진짜 7)으로 **한 번씩만** 잽니다. test 결과를 보고 설정을 다시 고르지 않습니다.
- C에서 고른 엔진(또는 2회차에서 채택한 전처리)은 아래를 **모두** 만족하면 확정합니다.
  1. 진짜 test 품목 F1 ≥ 기본 − 0.05 (진짜 test 품목 43개 중 약 2개)
  2. 진짜 test 합계를 맞힌 장수 ≥ 기본
  3. 가짜 test 품목 F1 ≥ 0.90
- 아니면 "dev 결과가 test에서 재현되지 않음"으로 보고 기본을 유지합니다.
- 한계: test의 진짜 사진은 7장이라, 품목 F1 0.05 안팎의 차이는 우연과 구별하기 어렵습니다. test로는 "크게 나빠지지 않았는지"를 확인합니다.

### 3. 엔진별 궁합 맞추기

엔진마다 읽는 버릇이 달라서, 그대로 비교하면 "엔진이 나빠서"가 아니라 "우리 파서와 안 맞아서" 점수가 낮게 나올 수 있습니다(2회차의 교훈).

| 대상 | 수정 | 이유 |
| --- | --- | --- |
| 파서 (모든 엔진) | 숫자 열 안의 낱말이 숫자처럼 생긴 글자로만 되어 있으면 숫자로 읽음 (`OOO` → `000`, `S,OOO` → `5,000`) | EasyOCR이 0을 영문 O로 자주 읽음 (`69, OOO`). 회귀 테스트 추가 |
| EasyOCR | `width_ths` 설정을 넘길 수 있게 함 | 0.1이면 가까운 낱말을 덜 합쳐 낱말 단위 상자가 됨 (표의 열 나누기에 유리할 수 있음) |
| PaddleOCR | 엔진 추가 + `words`(낱말 상자) · `unwarp`(문서 펴기) 설정 | 낱말 상자는 Tesseract의 낱말 위치와 같은 역할, 문서 펴기는 말린 종이 대응 |
| 도구 | `--engine 이름:설정=값`, bench `--prep`, ablation `--engine` · `--base` | 같은 엔진을 설정만 바꿔 비교 |
| 시간 측정 | 엔진의 첫 실행(모델 준비)은 시간에서 뺌 | 서버는 엔진을 한 번 만들어 계속 씀 |

PaddleOCR은 이 PC에서 돌리기까지 **설치 · 환경 문제** 세 가지를 풀어야 했습니다. 궁합이 아니라 실행 환경 문제이고, 해결법은 OCR README에 적었습니다.

| 문제 | 증상 | 해결 |
| --- | --- | --- |
| 기존 패키지와 충돌 | 설치 전 점검(dry-run): numpy 2.5 → 2.3으로 내려가고 OpenCV 패키지가 하나 더 설치됨 (같은 `cv2` 폴더를 덮어쓸 위험) | 별도 가상환경 |

### 4. 엔진 점수 (파서를 거치지 않은 인식 실력)

초안 점수(품목 F1)는 엔진 + 줄 묶기 + 파서를 합친 결과라서, 낮게 나와도 누구 탓인지 모릅니다. 그래서 엔진이 읽은 줄 글자만 보는 점수 두 개를 추가했습니다(`bench.engine_score`).

- **금액 인식률**: 정답 품목 금액이 엔진 원문에 숫자로 나타난 비율. `69, 000`처럼 천 단위 쉼표 옆의 띄어쓰기는 붙여서 보고,
  칸 사이 띄어쓰기(`1,680 1 1,680`)는 붙이지 않습니다. 영문 O로 읽은 숫자는 틀린 것으로 셉니다.
  같은 값이 여러 번 나오면 그만큼만 셉니다. 한계: 수량이 1인 품목은 단가와 금액이 같아서 두 번 찍혀 있으므로 한쪽만 맞게 읽어도 맞힌 것이 됩니다.
- **이름 인식률**: 정답 품목 이름과 유사도 0.7 이상인 부분이 원문 줄 어딘가에 있는 비율.

### 7. 결론

1. **PaddleOCR이 dev와 test 모두에서 기본보다 크게 낫습니다.** 진짜 사진 품목 F1이 dev 0.44 → 0.72, test 0.42 → 0.68이고, 합계도 dev 4/14 → 9/14, test 2/7 → 3/7입니다.

   다만 서비스의 기본값을 실제로 바꾸는 일(API · Worker 적용)은 이 실험의 범위 밖이라 8절의 다음 작업으로 남깁니다.
2. **차이는 엔진의 인식 실력에서 나옵니다.** PaddleOCR은 정답 금액을 dev 98% · test 100% 원문에 담았고 이름 인식률도 0.86 · 0.91입니다(Tesseract fast는 금액 0.77 · 0.72, 이름 0.62 · 0.63).
   반면 엔진 점수 차이가 작으면 초안 점수로 이어지지 않습니다. Tesseract best는 엔진 점수가 기본보다 조금 높지만(0.71 · 0.695) dev F1은 더 낮고(0.40), test에서는 엉뚱한 품목이 더 많았습니다(+14 · +9).
3. **영수증 종류에 따른 약점은 남아 있습니다.** 말린 식당 영수증(에이스돈 2장)에서는 PaddleOCR이 Tesseract보다 못하거나 비슷하고(dev_real_09: 0.36 vs 0.77),
   test_real_02(숯숯)에서도 금액은 8/8 읽고도 품목은 1/8에 엉뚱한 품목 6개였습니다. 엔진을 바꿔도 모든 사진이 나아지지는 않습니다(dev 14장 중 1장, test 7장 중 2장이 나빠짐).
4. **이제 병목은 파서입니다.** PaddleOCR은 test 진짜 사진의 금액을 모두 읽었지만 품목은 43개 중 32개만 맞혔고, 엉뚱한 품목이 19개 붙었으며, 합계는 7장 중 3장만 맞혔습니다.
   - dev_real_12(코스트코)는 금액 · 이름을 15/15 읽고도 품목 0/15입니다. 품목이 "이름 줄 + `상품코드 수량 단가 금액` 줄"의 두 줄 형식이라 파서가 묶지 못했습니다(dev에서 확인).
   - test_real_05는 세 엔진 모두 0점인데, PaddleOCR이 금액 · 이름을 3/3 읽었으므로 엔진이 아니라 파서 단계의 문제입니다. test 사진이므로 이것을 보고 규칙을 고치지는 않습니다.
5. **딥러닝 엔진에는 흑백 이진화가 해롭습니다.** PaddleOCR 12개 설정 중 ②⑥(자르기 + 적응형 이진화)을 쓴 4개가 모두 가장 나빴습니다(진짜 F1 0.53 ~ 0.59, 나머지 0.63 ~ 0.72, 금액 인식 0.98 ~ 0.99 → 0.80 ~ 0.82).
   Tesseract에서는 ②⑥이 금액 인식을 올렸던 것(0.77 → 0.89)과 반대입니다. 낱말 상자(`words=true`)는 PaddleOCR의 줄 상자보다 나을 것이 없었습니다(같은 설정에서 진짜 F1이 같거나 0.01 ~ 0.05 낮음).
6. **EasyOCR은 이번 용도에 맞지 않습니다.** 깨끗한 가짜 영수증에서도 F1이 0.76 ~ 0.84로 탈락했고, 진짜 F1(0.26 ~ 0.37)도 기본보다 낮으며 진짜 사진에서 장당 9 ~ 13초가 걸립니다.

## 4회차 — 파서 개선: 마트형 영수증 (2026-11-24)

3회차에서 PaddleOCR로 엔진을 바꾼 뒤에는 엔진이 글자를 다 읽고도 파서가 품목 · 합계를 놓치는 경우가 남았습니다(3회차 결론 4).
이번 회차는 파서를 두 단계로 고치고, test는 두 단계가 모두 끝난 뒤 한 번만 잽니다.

- 4-1. 숫자 줄 품목 읽기
- 4-2. 세금 줄 산수로 합계 찾기 (계획 때 이름은 '합계 아래 줄 막기 + 세금 줄 검산')
- 4회차 test: 마트형 test 사진 4장을 더한 뒤 두 단계를 합친 파서로 한 번

### 4-1. 숫자 줄 품목 읽기

#### 1. 발견한 문제

코스트코 영수증(dev_real_12)은 PaddleOCR이 금액 · 이름을 15/15 모두 읽었는데 품목은 0/15였습니다.
이 영수증은 품목이 "이름 줄 + `상품코드 수량 단가 금액 T` 줄"의 두 줄로 찍힙니다.
두 줄을 합치는 규칙(`_merge_two_line_items`)은 1회차부터 있었지만, 그 주변 규칙에서 막혔습니다.
dev 진짜 사진 14장을 두 엔진으로 읽어 줄마다 어떻게 판단했는지 확인했습니다.

| # | 증상 (dev에서 본 실제 줄) | 원인 | 사진 |
| --- | --- | --- | --- |
| S1 | `680231 1 32,990 32,990 T`, `27,980T` | 금액 뒤 과세 표시 `T` 때문에 숫자 줄로 보지 않아 두 줄을 합치지 못함 | 코스트코 |
| S2 | `1,000-T` (쿠폰 할인) | 금액 뒤에 붙은 `-`를 빼기로 읽지 못함 | 코스트코 |
| S3 | 품목 중간의 `상품수 소계:5` | 금액이 없는 '소계' 줄인데 품목 구간을 끊어, 그 아래 품목 11개를 버림 | 코스트코 |
| S4 | `689637 프라이드치킨 1 17,970 …` | 이름 앞 상품코드가 이름에 붙어 이름이 틀림 | 코스트코 |
| S5 | `9,790 9, 790 T` | 표 머리줄이 없는 영수증에서 띄어 읽힌 천 단위를 790으로 읽음 | 코스트코 |
| S6 | `칠성사이다 210m1 10` 다음 줄 `8801056095086 5,480 1 5,480` | 이름 끝(`*10`)이 숫자로 읽혀 '이름만 있는 줄'이 아니게 됨 → 합치지 못하고 10원짜리 엉뚱한 품목이 생김 | 이마트(dev_real_11) |
| S7 | `(농할행사) 26년 11 2 -300` | 할인 낱말 없이 빼기 금액만 있는 할인 줄을 버림 (코스트코의 쿠폰 할인 3줄도 같음) | 농협(dev_real_10) |

다른 사진의 엉뚱한 품목(`한계수량/금액 3 7,589`, `관세 매출 6,436`, `세 물 24,018`)은 합계 · 세금 줄을 품목으로 잡은 것이라 4-2에서 다룹니다.
Tesseract는 코스트코 영수증을 거의 읽지 못해서(`69235 1 24.270 _ 24.2707 뽀 60000 한우곰탕 …`), 이번 수정의 효과는 PaddleOCR에서 납니다.

#### 2. 고치는 방향과 위험 (구현 전에 확인)

- **일반 규칙** (영수증 형식과 무관한 구조): S3 · S5 · S6 · S7.
  S6은 "다음 줄이 숫자만 있고 단가 × 수량 = 금액이 맞으면"으로 넓혀서, 산수가 맞을 때만 합칩니다.
- **형식 전용 규칙** (창고형 마트 계산대 형식): S1 · S2 · S4. 그 글자(`T`, 금액 뒤 `-`, 이름 앞 5자리 이상 숫자)가 있을 때만 발동합니다.
- **부작용 가늠**: 코스트코를 뺀 dev 13장(식당 · 카페 7장 포함)에서 규칙이 발동할 만한 줄을 두 엔진 결과로 셌습니다(파서를 거친 글자로 센 근사치).
  - 식당 · 카페 7장에서는 두 엔진 모두 0줄이었습니다.
  - PaddleOCR에서는 S7만 농협 사진의 3줄에서 발동합니다. 1줄은 목표인 할인 줄이고, 2줄은 합계 아래라 품목 구간 밖입니다.
  - Tesseract에서는 S5만 10줄에서 발동합니다. 8줄은 이미 무시하는 세금 · 카드 줄이고, 2줄은 GS25 품목 줄입니다(`3, 300` → 3,300으로 바로잡힐 것으로 예상).
- **한계 (과적합)**: 형식 전용 규칙은 코스트코 한 장을 보고 만든 것입니다. 다른 영수증을 해치지는 않더라도 다른 마트에서도 도움이 되는지는 알 수 없고, dev F1 상승도 대부분 그 한 장에서 나올 것입니다.
  그래서 코스트코를 뺀 점수도 함께 적습니다. 지금 test 진짜 사진은 식당 · 카페 6장 + 아울렛 1장이라 마트 규칙이 처음 보는 영수증에서도 통하는지는 test로 확인할 수 없습니다.
  마트형 test 사진을 더 넣은 뒤 확인할 예정입니다.

#### 3. 채택 규칙 (구현 전에 정함)

- 기준: 3회차 끝의 파서(커밋 `3db8c9f`). 엔진은 PaddleOCR(`unwarp=true` + 최소 전처리, 주 엔진)과 Tesseract fast(기본 전처리, 보조) 두 가지이고, 기준 점수는 3회차 dev 결과입니다.
- 아래를 **모두** 만족하면 채택합니다.
  1. PaddleOCR 진짜 dev 품목 F1 > 기준
  2. 진짜 dev 14장 중 기준보다 사진별 품목 F1이 나빠진 사진이 **0장** (두 엔진 모두).
     파서 규칙은 결과가 매번 같고 특정 증상을 겨냥하므로, 나빠진 사진이 있으면 규칙이 넘친 것으로 봅니다. 나빠지면 dev에서 원인을 보고 고친 뒤 다시 잽니다.
  3. 진짜 dev 합계를 맞힌 장수 ≥ 기준 (두 엔진 모두)
  4. 가짜 dev 품목 F1 ≥ 기준 (두 엔진 모두)
  5. 자동 테스트 통과
- 규칙별 효과: OCR 결과를 한 번 저장해 두고 파서만 다시 돌려, 일반 규칙 → 형식 전용 규칙 순으로 하나씩 더하며 사진별로 무엇이 바뀌었는지 기록합니다.
- 점수는 마트형(dev_real_01 · 04 · 06 · 10 · 11 · 12 · 14)과 식당 · 카페형(dev_real_02 · 03 · 05 · 07 · 08 · 09 · 13)으로 나누고, 코스트코를 뺀 F1도 적습니다.
- test는 4-2까지 끝난 뒤 한 번만 잽니다. 3회차 D 규칙을 두 엔진에 적용하고, 기준은 3회차 test 점수입니다.

### 4-2. 세금 줄 산수로 합계 찾기

#### 1. 발견한 문제

계획할 때 이름은 '합계 아래 줄 막기 + 세금 줄 검산'이었습니다. 그런데 dev를 확인해 보니 **합계 낱말을 찾은 영수증에서는 이미 합계 줄 아래를 품목으로 보지 않고 있었습니다.**
남은 문제는 두 가지였습니다 (PaddleOCR, 4-1 파서 기준).

| # | 증상 | 사진 |
| --- | --- | --- |
| 1 | **합계 낱말을 못 읽은 영수증**: 합계가 비고, 품목 구간의 끝이 없어 아래쪽 줄까지 품목이 됨 | 이마트 · 코스트코 · 주스 가게 · 주유소 (dev_real_11 ~ 14) |
| 2 | **낱말이 틀어진 세금 줄이 품목이 됨**: `관세 매출 6,436` · `분가세 644`, `세 물 24,018` · `가 2,402`, `순 4,091` · `부 가 세 409`. 무시할 낱말 목록에 걸리지 않음 | GS25 · 이마트 · 주스 가게 |

둘 다 **"부가세 = 공급가의 10%"라는 산수**로 풀 수 있습니다. 낱말을 보지 않고 산수 조건(아래 2절)만으로 dev 20장을 두 엔진 결과에서 찾아봤습니다.

| | PaddleOCR | Tesseract |
| --- | --- | --- |
| 세금 짝 줄을 찾은 사진 | 14장 (가짜 6 + 진짜 8) | 6장 (가짜 5 + 진짜 1) |
| 세금 합(+ 면세) = 정답 합계 | **14장 모두** | **6장 모두** |
| 틀린 합계를 만든 짝 | 0 | 0 |

예: 이마트(dev_real_11)는 면세 65,380 + 과세 24,018 + 부가세 2,402 = 91,800, 코스트코(dev_real_12)는 56,890 + 180,863 + 18,087 = 255,840으로 정답 합계와 같습니다.
(계획 때는 PaddleOCR 진짜 사진을 9장으로 보고했는데, 보고서를 쓰며 다시 세어 보니 8장이었습니다.)

#### 2. 고치는 방향과 위험 (구현 전에 확인)

- **세금 짝 줄의 조건**: 금액이 하나뿐인 줄 두 개가 2줄 안에 있고, 뒤 줄이 앞 줄의 10% ± 1원이며, 앞 줄 금액이 100원 단위로 떨어지지 않을 것.
  마지막 조건은 `20,000원` 다음 `2,000원` 같은 가격 줄과 구별하려고 넣었습니다. 바로 위 3줄 안에 '면세' 줄이 있으면 그 금액도 세금 합에 더합니다.
- **일반 규칙**입니다. 한국 영수증의 부가세(10%) 구조라 특정 가게 형식에만 있는 것이 아닙니다.
  식당 · 카페형 dev 7장 중 주스 가게를 뺀 6장은 짝이 없거나 이미 찾은 합계와 같은 값만 나와서 바뀌지 않을 것으로 가늠했습니다.
- **위험**: 마트 가격은 `2,490`처럼 100원 단위가 아닌 경우가 많아, `2,490원` 품목 바로 다음에 `249원` 품목이 오면 세금 줄로 볼 수 있습니다. dev에서는 이런 경우가 없었습니다.
- **제외**: 농협 합계(할인을 반영해야 하는 문제라 S7과 함께 남김), `합계수량/금액`을 `한계수량/금액`으로 읽은 줄, 이름 오인식(에이스돈 등).

#### 3. 채택 규칙 (구현 전에 정함)

구현과 결과 확인 전(2026-11-24 18:52)에 적어 두었습니다. 4-1과 다른 점은 **합계가 O → X로 바뀐 사진도 '나빠짐'으로 센 것**입니다(이번 목표가 합계라서).

- 기준: 4-1 커밋(`287758b`)의 파서. 엔진과 평가 데이터(dev 20장)는 4-1과 같습니다.
- 아래를 **모두** 만족하면 채택합니다.
  1. PaddleOCR 진짜 dev 합계를 맞힌 장수 > 기준
  2. PaddleOCR 진짜 dev 품목 F1 ≥ 기준
  3. 나빠진 사진 0장 (두 엔진). 나빠짐 = 사진별 품목 F1 하락 또는 합계 O → X
  4. 가짜 dev 품목 F1 · 합계 ≥ 기준 (두 엔진)
  5. 자동 테스트 통과
- 점수는 영수증 종류별로 나누고, 코스트코를 뺀 점수도 적습니다.
- test는 마트형 test 사진을 더한 뒤 4-1 · 4-2를 합친 파서로 한 번 잽니다(아래 4회차 test).

| # | 구현 |

#### 4. 결론

1. **확정했습니다.** test에서도 PaddleOCR 진짜 F1이 0.701 → 0.724, 합계가 3/11 → 5/11로 dev와 같은 방향입니다. 다만 크기는 dev(F1 0.717 → 0.869, +0.15)보다 훨씬 작습니다.
   dev 상승의 대부분이 코스트코 한 장(4-1)에서 나왔는데, test에는 4-1이 겨냥한 형식의 영수증이 코스트코 1장(품목 2개)뿐이었기 때문으로 봅니다.
2. **4-1의 형식 전용 규칙(S1 · S2 · S4)이 다른 마트에서도 통하는지는 이번 test로도 확인되지 않았습니다.** 발동한 곳은 같은 가게인 코스트코 영수증 1장(쿠폰 할인 1개)뿐이고,
   dev에 없는 가게의 마트 영수증 3장(207피트 2장 · 빅마트)은 형식이 달라 발동하지 않았습니다. 해치지도 돕지도 않았으므로 "코스트코 형식에 맞춘 규칙"이라는 한계는 그대로입니다.
3. **4-2(세금 줄 산수)는 처음 보는 영수증에서도 작동했습니다.** 식당 1장(무정집)과 dev에 없는 마트 1장(빅마트)의 합계를 새로 맞혔고, 틀린 합계를 만든 경우는 없었습니다.
   일반 규칙으로 만든 것이 형식 전용 규칙보다 처음 보는 사진에서 더 잘 통했습니다.
4. **사진별 F1이 점수 이상으로 엄격한 경우가 있습니다.** test_real_10은 품목을 새로 찾아 금액까지 맞혔는데 이름 때문에 점수가 내려갔습니다.
   사람이 초안을 고치는 입장에서는 빈칸보다 나은 결과라서, 사진별 하락은 원인까지 보고 판단해야 합니다.
5. **test에서 본 남은 문제** (test 사진이므로 이것을 보고 규칙을 고치지 않습니다. 고치려면 같은 증상을 dev에서 찾아 만들고, 효과는 새 test 사진으로 잽니다):
   - 한 줄에 금액이 두 개인 세금 줄(207피트 2장): 세금 합을 쓰지 못하고, `판매금액` · `받을금액` 줄이 품목이 됨
   - 할인을 반영한 합계(금촌농협 2장, dev_real_10과 같은 문제)와 이름에 '쿠폰'이 들어간 품목을 할인으로 읽는 것(`[소비쿠폰] 판란` → −9,300)
   - 이름 앞 줄 번호(`003P`)가 이름에 남는 것, 할인 열(`0`)이 낀 두 줄 품목(무정집, 3회차부터)
6. **한계**: 진짜 test는 11장이고, 그중 dev에 없는 가게의 마트형은 3장(가게 2곳)입니다. F1 0.02 차이는 우연과 구별할 수 없고, 이번 test로는 "나빠지지 않았는지"와 "4-2가 처음 보는 사진에서도 맞는 합계만 만드는지"를 확인했습니다.
